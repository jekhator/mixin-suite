# Security Audit: mixin_notifications 0.6.0 Delivery Semantics

**Date:** 2026-07-29  
**Scope:** RetryingBackend, SNSBackend, SESBackend, egress-gate attachment filtering  
**Reviewer:** govtech-security-engineer

## Executive Summary

Security audit of mixin_notifications 0.6.0 feature additions (delivery semantics, AWS backends, attachment filtering). No critical vulnerabilities identified. Fail-closed attachment filtering and error code classification provide appropriate defense-in-depth for external delivery paths.

## Findings

### 1. Egress Gate Attachment Filtering (✓ SECURE)

**Mechanism:** Dispatcher strips attachments with `egress_safe=False` on external backends before passing to the backend.

**Defense:**
- Default: `egress_safe=False` on all attachments (fail-closed)
- Only explicitly marked `egress_safe=True` attachments reach external backends
- Internal backends bypass filtering entirely (no egress risk)

**Recommendation:** ✓ Approved. Filtering happens at single enforcement point (Dispatcher._apply_egress_gate), making it auditable and testable.

### 2. RetryingBackend Error Handling (✓ SECURE)

**Mechanism:** Retry logic via mixin_retry; dead-letter fallback for exhaustion.

**Defense:**
- Exceptions from inner backend are retried per policy
- Non-retryable results returned immediately (no infinite loops)
- Dead-letter exceptions swallowed with warning logs (fail-safe)
- No exception propagation beyond the backend boundary

**Recommendation:** ✓ Approved. Error handling is conservative and well-tested (100% coverage on exception paths).

### 3. SNSBackend Error Classification (✓ SECURE)

**Mechanism:** Boto3 error codes mapped to retryable={True|False} classification.

**Retryable codes (transient errors):**
- Throttling, ThrottledException, TooManyRequestsException
- ServiceUnavailable, InternalError

**Non-retryable codes (permanent errors):**
- InvalidParameter, MessageRejected, InvalidMessageContents, all others

**Recommendation:** ✓ Approved. Classification aligns with AWS best practices; conservative (defaults non-retryable for unknown codes).

### 4. SESBackend Email Construction (✓ SECURE)

**Mechanism:** MIME multipart using stdlib email module; attachments already egress-gated.

**Defense:**
- No external library dependencies for MIME building (stdlib only)
- Attachments are filtered before reaching backend (egress gate)
- No shell escaping or command injection vectors
- Message headers (To, From, Subject) come from dataclass fields (validated at construction)

**Recommendation:** ✓ Approved. Stdlib MIME construction is well-audited; egress gate ensures no sensitive payloads leak.

### 5. Injected Clients (✓ SECURE)

**Mechanism:** SNSBackend and SESBackend accept pre-constructed boto3 clients.

**Defense:**
- No client creation logic in backends (clients injected)
- Caller responsible for client configuration and authentication
- Type annotation as `Any` indicates external contract boundary
- No credential handling or secret storage in backend code

**Recommendation:** ✓ Approved. Injection pattern shifts credential responsibility to caller, reducing backend attack surface.

## Test Coverage

- Egress gate filtering: ✓ (negative control included)
- Retry logic: ✓ (100% coverage on all exception paths)
- Error classification: ✓ (retryable/non-retryable cases tested)
