## Executive Summary

Review of mixin_notifications 0.6.0 surface additions for API design, modularity, and backward compatibility. Design is sound: frozen+slots dataclasses, zero public module-level functions, clean separation of concerns (Attachment/Event, Dispatcher/Backend), and full backward compatibility maintained.

## Design Review

### 1. Attachment DTO (✓ APPROVED)

**Design:**
```python
@dataclass(frozen=True, slots=True)
class Attachment:
    filename: str
    content_type: str
    content: bytes
    egress_safe: bool = False
```

**Strengths:**
- Frozen: immutable, hashable, thread-safe
- Slots: memory efficient for large attachment collections
- Validation in `__post_init__`: prevents empty filename/content_type
- `egress_safe` default=False: fail-closed (default to private)

**Assessment:** ✓ Solid DTO design. Follows qhcg frozen-slots pattern exactly.

### 2. NotificationEvent Extension (✓ APPROVED)

**Change:** Added `attachments: tuple[Attachment, ...] = ()` as LAST field

**Backward Compatibility:**
- Default value ensures old code works unchanged
- LAST field position allows subclasses to add fields after
- Tuple type prevents accidental mutation

**Assessment:** ✓ Excellent design for extensibility. Default placement is canonical.

### 3. RetryingBackend Wrapper (✓ APPROVED)

**Design:**
```python
@dataclass(frozen=True, slots=True)
class RetryingBackend:
    inner: NotificationBackend
    policy: RetryPolicy
    dead_letter: NotificationBackend | None = None
```

**Strengths:**
- Composition over inheritance (wraps, doesn't extend)
- Composes mixin_retry's RetryExecutor (no custom retry loop)
- Dead-letter is optional, allowing gradual adoption
- Combines external_egress via OR logic (any egress = external)

**Concern Resolved:** RetryableDeliveryError is an internal adapter (not exposed in public API); normalized to exception for retry engine. Design is sound.

**Assessment:** ✓ Clean composition pattern. Reuses mixin_retry as intended.

### 4. SNSBackend and SESBackend Separation (✓ APPROVED)

**Design:** Moved to separate modules (`backends/sns.py`, `backends/ses.py`) to respect LOC cap.

**Modularity:**
- One backend per file (SNS: 33 lines, SES: 38 lines)
- backends/_client.py stays under 300 lines (79 lines for base + RetryingBackend)
- Root exports via backends/__init__.py unchanged

**Boto3 Integration:**
- `sns_client` and `ses_client` are injected (type: Any)
- No credential handling in backend code
- Error classification maps boto3 codes to retryable={True|False}

**Assessment:** ✓ Excellent modularity. Respects LOC constraints without sacrificing clarity.

### 5. Egress Gate Extension (✓ APPROVED)

**Design:** Dispatcher._apply_egress_gate now filters attachments.

**Mechanism:**
```python
safe_attachments = tuple(att for att in event.attachments if att.egress_safe)
# Safe attachments sent to external backend; unsafe stripped
```

**Single Enforcement Point:**
- Dispatcher is the only place attachments are filtered
- All backends receive consistent treatment (external vs. internal)
- Attachment filtering is NOT backend-specific (centralized)

**Assessment:** ✓ Textbook defense-in-depth. Single point of enforcement, testable with negative controls.

## Concerns Addressed

1. **Q: Why composition over inheritance for RetryingBackend?**  
   A: Composition allows flexible nesting (RetryingBackend(inner=RetryingBackend(...))). Inheritance would break Liskov Substitution Principle due to policy parameter.

2. **Q: Why is `egress_safe` on Attachment, not on NotificationEvent?**  
   A: Attachment-level granularity: different attachments in same event can have different egress safety. Event-level flag would be too coarse.

3. **Q: Why optional dead_letter instead of required?**  
   A: Adoption is gradual. Retries without dead-letter are valid; dead-letter adds optional resilience on top.
